11. 実践：README を書く

この章では、これまでに学んだ記法を使って、プログラムの説明書である README を書く。また、GitHub の Issue やプルリクエストで Markdown を使うときのポイントも説明する。

11.1. README とは

README は、プログラムやリポジトリの概要、使い方などを説明する文書である。GitHub では、リポジトリの一番上のフォルダに README.md を置くと、リポジトリのページを開いたときに、ファイルの一覧の下にその内容が表示される。README は、そのリポジトリを初めて見た人が最初に読む文書である。

11.2. README に書く項目

README に書く項目に決まりはないが、一般に次のような項目を書く。上から順に、読み手が知りたい順に並べるとよい。

表 11.1 README に書く主な項目

項目

内容

名前と概要

何をするプログラムなのかを 1、2 文で書く。読み手は、最初の数行を読んで、自分に関係があるかどうかを判断する

必要な環境

動作に必要な OS、言語のバージョン、他のソフトウェアなど

インストール

インストールの手順。実行するコマンドをそのまま書く

使い方

基本的な使い方と実行例

ライセンス

プログラムを利用する条件。ライセンスの文書（LICENSE ファイル）へのリンクを書くことが多い

規模の大きいプロジェクトでは、開発に参加する方法、問い合わせ先、変更履歴へのリンクなどを加える。逆に、個人の小さなプログラムなら、概要と使い方だけでも十分である。

11.3. 悪い例を書き直す

  • 見出しを使っていないので、項目の区切りが分からない（1、3、5、8 行目）。

  • 1 回の改行では改行されないため、すべての行がつながって表示される。

  • コマンドをインラインコードやコードブロックにしていないので、どこまでが入力するコマンドなのか分からない（4、6 行目）。

  • 複数のコマンドの説明を 1 文に詰め込んでいる（6 行目）。

  • ファイル名をインラインコードにしていないので、.todo.json の先頭の . を見落としやすい（7 行目）。

  • 英数字の前後に空白がなく、文体も「です・ます」と「である」が混ざっている。

書き直した README では、次の点を改めた。

  • タイトルを #、各項目を ## の見出しにした。GitHub では、見出しから目次が自動で作られる。

  • インストールのコマンドを、言語名を指定したコードブロックにした。読み手はコマンドをそのままコピーできる。GitHub では、コードブロックの右上にコピーのボタンが表示される。

  • コマンドの一覧を表にまとめ、続けて実行例をコードブロックで示した。実行例の言語名の console は、行頭の $ が入力、それ以外が出力であることを表す書き方である。

  • 注意すべき点をアラートで目立たせた。

  • ライセンスの文書へ相対パスでリンクした。

README を書くときは、初めてリポジトリを見た人の立場で読み返し、「何のプログラムか」「どうすれば動かせるか」がすぐに分かるかを確かめるとよい。

11.4. Issue とプルリクエスト

GitHub の Issue やプルリクエストの本文とコメントも Markdown で書ける。.md ファイルと同じ記法が使えるが、次の点が異なる。

  • 1 回の改行がそのまま改行として表示される（第 4 章）。

  • # に続けて番号を書くと（例：#123）、その番号の Issue やプルリクエストへのリンクになる。

  • @ に続けてユーザー名を書くと、その人に通知が送られる（メンション）。

  • タスクリストのチェックボックスを、画面上で切り替えられる（第 6 章）。

不具合を報告する Issue では、「発生した現象」「再現する手順」「期待する結果」「実行環境」を見出しで区切り、エラーメッセージはコードブロックに入れて書くと、読み手が状況を理解しやすい（第 7 章のサンプルを参照）。

Issue やプルリクエストを毎回同じ形式で書いてほしいときは、リポジトリにテンプレートを置ける。たとえば .github/pull_request_template.md という Markdown のファイルを置くと、プルリクエストを作るときに、その内容が本文の入力欄にあらかじめ入力される。Issue のテンプレートは .github/ISSUE_TEMPLATE フォルダに置く。

11.5. コミットメッセージ

Git のコミットメッセージは、Markdown として表示されない。GitHub でコミットメッセージを表示しても、# で始まる行が見出しになったり、** で挟んだ文字が強調になったりすることはない。そのため、コミットメッセージに Markdown の記法を使う必要はない。

ただし、プレーンテキストのままでも読みやすいという点で、Markdown と同じ考え方が役に立つ。コミットメッセージは、1 行目に変更の要約を短く書き、1 行空けて、3 行目以降に詳しい説明を書くのが一般的である。説明の中で変更点を並べるときは、行頭に - を付けた箇条書きの形がよく使われる。

リスト 11.1 コミットメッセージの例
1ログイン画面に入力チェックを追加する
2
3- メールアドレスの形式が正しくない場合にエラーを表示する
4- パスワードが空の場合に送信ボタンを押せないようにする
